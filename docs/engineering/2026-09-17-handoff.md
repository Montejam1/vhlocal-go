### Important limitations to retain in the engineering review

- Lexical scope and source-line identity are not Python AST parity. Multiline
  statements, nested scopes, ambiguous citations, and non-Python targets need
  additional fixtures. Conservative identities can increase verification workload.
- Matching a decision to a manifest revision is not a complete dirty-tree snapshot
  mechanism. Review non-git and working-tree freshness, plus resume against changed
  target code; do not overstate revision guarantees.
- Sink-dependent acceptance can block logic/authorization findings. One saved
  unresolved rationale explicitly cites inability to recognize a CWE-284 write as
  a sink. Compare Python's handling of "not assessable syntactically" with Go's
  boolean requirement in `validateEvidenceBacked`; retain substantive evidence.
- Artifact feedback is recorded after the reproduction agent finishes; there is no
  bounded correction loop that lets it repair invalid registrations or headers.
- Structural artifact validation checks for an assertion, not whether the test
  proves security impact or has a meaningful negative control. No generated test
  was run as part of the previous validation.
- Go-only transcript goldens originated from Go; independent reference contracts
  cover bounded validation cases only. Neither establishes live scanner recall,
  full report parity, application API compatibility, or browser correctness.

## Starting points for the engineering investigation

### Applications and intelligence discovery — confirmed contract mismatch

`internal/server/handlers.go:handleApplications` returns `apps.List()` and
`handleApplication` returns a raw registry entry. Compare with Python
`../vhlocal/vhlocal/server.py:_apps_index`, `_app_summary`, `_applications`,
`_application_detail`: Python joins registry entries, saved reports and ledgers.

Consumers are `web-react/src/lib/types.ts` (`AppSummary`, `AppDetail`),
`pages/Applications.tsx`, and the shipped `vhlocal/web/index.html` Apps view. Their
history/intelligence discovery requires fields the Go server does not supply.
`engine.go` also calls `apps.Register` only in the ledger-enabled branch. A scan
must be discoverable as an application even with ledger disabled, as in this run.
Keep hidden/forgotten-app semantics and preserve existing report files.

### Scans — user-visible failure, root cause not yet established

Eight jobs are returned locally. Inspect the actual page used by the operator:
`/` serves `vhlocal/web/index.html`; `/app/...` serves the embedded React bundle;
`/legacy` and `/classic` are additional surfaces. Capture the first JavaScript
exception and failed request on each supported route. Check startup failures,
polling/SSE errors, mixed persisted job shapes, nullable values, deep links, and
embedded asset freshness. `usePoll` stores errors that Scans does not display.
Do not silently convert transport/schema errors into "No scans yet."

### Completion — confirmed queue/engine/UI disagreement

`internal/server/server.go:runScan` treats a nil engine error and empty `Aborted`
as success. `internal/jobs/jobs.go` then marks the job done. The engine deliberately
finalizes partial scans without returning a fatal error. React `StepTracker.tsx`
converts `job.status === 'done'` into "All N steps complete" and marks every step
successful. Propagate observed phase outcomes and the three status axes; queue
termination is not evidence that all scan phases completed. Inspect the equivalent
root UI tracker as well. Do not replace useful partial results with an opaque error.

### Threat/SBOM — generation, retrieval and presentation must be tested separately

For this run both files are present and retrievable. Restore app/report navigation
and downloads first; test requested-but-failed and explicitly-disabled runs too.
SBOM generation currently sits inside the Phase-1t success path and its write
error is discarded (`_, _ = sbom.Write(...)`). Define explicit artifact status and
surface generation/parse/read errors. Do not fabricate missing artifacts or silently
rerun old scans merely to populate the UI.

### Verification and reproduction — live-model acceptance remains unfinished

Inspect the 72 tool-repair and 26 max-turn exits. Record actual rejected tool calls,
validation messages, context/line coverage needs, and repair budgets per candidate.
Avoid solving the 98 missing decisions by accepting incomplete reviews, weakening
requirements, or increasing retries without measurement. Review authorization/
logic findings independently of syntactic injection-sink detection.

Phase 3 generated real material but six test bindings failed validation. Provide
bounded actionable repair feedback, persist progress, and allow a specific deferral
when reliable material cannot be authored. Keep unsupported candidates out of the
reproduction assignment. Preserve current failing output as regression evidence.

### Report quality — deterministic output needs richer content

`internal/report/report.go` renders a short field list per finding despite stored
verification reasoning/evidence; README now uses that same renderer. Compare the
Python report/consolidation code and the user workflow, not just JSON key presence.
A useful report must prioritize supported findings; retain rejected/unresolved
candidates in clearly identified sections; explain attacker control, preconditions,
defenses, impact, source excerpts, remediation and verification limits; link valid
artifacts and deferrals; expose threat model, SBOM, coverage and phase failures.
Raw candidate count must not read as confirmed vulnerability count. The latest
90,231-byte report has 140 candidates, only 10 labeled supported.
